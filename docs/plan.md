# План работ

Живой документ. Меняется решение — меняется этот файл, в том же коммите, что и код.
Первоисточник требований — `TASK.md`, не этот документ.

## Цель

Одностраничный чат с языковой моделью через OpenRouter: потоковый вывод, прерываемая генерация,
внятные состояния на ошибках, доступность с клавиатуры, ключ на сервере.

Порядок, в котором задание обещает оценивать, — он же порядок приоритетов при нехватке времени:

1. Работоспособность и обработка краёв
2. Инженерные решения: где живёт ключ, как устроены стриминг и отмена
3. Процесс: коммиты, PR, README, ИИ-лог
4. Суждение: что замечено в задании и как обосновано
5. Вкус в интерфейсе

## Порядок работ: сначала мок

Сначала пишется мок-сервер, полностью имитирующий модель, и на нём **целиком** закрывается UI.
Реальный OpenRouter подключается последним.

Почему так:

- UI зависит не от OpenRouter, а от контракта потока. Контракт можно зафиксировать до того,
  как появится хоть один живой запрос.
- Мок делает воспроизводимым то, что на бесплатной модели ловится только везением: 429, таймаут,
  обрыв на середине, очень медленная и очень быстрая генерация. Эти состояния — первый пункт
  критериев оценки, и проверять их «когда-нибудь само выпадет» нельзя.
- Разработка UI не жжёт бесплатную квоту и не требует ключа. Проект запускается и проверяется
  без секретов вообще.
- Когда доходит очередь до живой модели, непроверенным остаётся ровно один модуль — адаптер.

Цена решения одна: контракт должен быть описан до обеих реализаций и соблюдаться обеими.
Поэтому он ниже, и поэтому правка контракта — это правка мока, адаптера и этого раздела
одним коммитом.

## Контракт API

Браузер ходит **только** на свой origin. Внешних запросов со страницы нет.

### `POST /api/chat`

Запрос:

```json
{
  "messages": [
    { "role": "user", "content": "Привет" },
    { "role": "assistant", "content": "Здравствуйте" }
  ],
  "model": "vendor/name:free"
}
```

`model` необязателен — без него берётся дефолт сервера. Историю целиком шлёт клиент: сервер
не хранит состояние между запросами.

Успешный ответ — `200` и `text/event-stream`:

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

События:

```
event: delta
data: {"text":"Lorem ipsum "}

event: error
data: {"code":"upstream_error","message":"Модель оборвала генерацию"}

event: done
data: {"reason":"stop","model":"mock/lorem","chars":812}
```

- `delta` — приращение текста. Именно приращение, не накопленный текст: клиент склеивает сам.
- `done` — нормальное завершение. `reason`: `stop` (модель закончила) | `length` (упёрлась в лимит).
- `error` — терминальное событие. После него поток закрывается.

Раз в 15 секунд сервер шлёт строку-комментарий `:` — keepalive против прокси, режущих простаивающие
соединения. Клиентский парсер обязан такие строки игнорировать (OpenRouter шлёт свои
`: OPENROUTER PROCESSING` — поведение одинаковое, и это удобно: парсер проверяется на моке
в тех же условиях).

### Ошибки

Правило, определяющее всю обработку: **как только отправлен первый байт тела, HTTP-статус изменить
уже нельзя.** Отсюда две разные формы ошибки, и никогда обе сразу.

До начала потока — обычный JSON и осмысленный статус:

```json
{ "error": { "code": "rate_limited", "message": "Модель занята", "retryAfter": 12 } }
```

| `code` | Статус | Когда |
|---|---|---|
| `bad_request` | 400 | пустые `messages`, неизвестная модель |
| `rate_limited` | 429 | квота бесплатной модели исчерпана; по возможности с `retryAfter` |
| `upstream_error` | 502 | апстрим ответил ошибкой |
| `upstream_unavailable` | 503 | до апстрима не достучались |
| `timeout` | 504 | первый токен не пришёл за отведённое время |
| `internal` | 500 | всё остальное |

После начала потока — событие `error` с теми же `code` и `message`, затем закрытие.
Уже отправленные `delta` остаются в силе: частичный ответ — валидный результат, а не мусор.

`message` — человекочитаемый текст для показа пользователю. Он **никогда** не содержит
деталей апстрима, заголовков и тем более ключа.

### Отмена

Клиент прерывает `fetch` через `AbortController`. Сервер ловит `close` на запросе раньше, чем
отдал `done`, и абортит upstream-запрос.

Последнее звено обязательно: без него нажатие «Стоп» останавливает только показ, а генерация
продолжает жечь бесплатную квоту. Отмена — не ошибка: сервер не пишет её в лог как сбой и не
пытается ничего дослать в закрытый сокет.

### `GET /api/models`

```json
{
  "models": [{ "id": "vendor/name:free", "name": "Name", "contextLength": 32768 }],
  "default": "vendor/name:free"
}
```

### Таймауты

| Что | Значение | Смысл |
|---|---|---|
| До первого токена | 30 с | бесплатные модели могут долго стоять в очереди |
| Между чанками | 20 с | поток замер — считаем мёртвым |
| Всего на запрос | 120 с | верхняя граница |

Значения — из env, в таблице дефолты.

## Фаза 1 — мок-сервер

Ветка `feat/mock-server`.

Express, маршруты по контракту, флаг `MOCK=1` (в разработке — дефолт). Отдаёт lorem ipsum.

- **Длина ответа случайная** — 200–1500 символов, обрезка по границе слова.
- **Чанки по 1–5 слов**, пауза 15–80 мс между ними, задержка первого токена 200–1200 мс.
  Разная скорость — чтобы UI проверялся и на «сыплется быстрее, чем рисуется», и на «еле капает».
- **Иногда с markdown** — заголовок, список, `**жирный**`, блок кода. Иначе рендер markdown
  будет проверен один раз руками и сломается незаметно.
- **Кадры SSE иногда режутся посреди события** между записями в сокет. Это не вредность:
  границы TCP-чанков не совпадают с границами событий, и клиентский парсер, который этого не
  переживает, ломается только в проде. Мок обязан ловить такое сразу.
- **Режимы отказов** через `?simulate=`:

  | Значение | Что делает |
  |---|---|
  | `429` | отвечает `rate_limited` с `retryAfter` до начала потока |
  | `timeout` | держит соединение и не шлёт первый токен |
  | `drop` | обрывает соединение на середине без `done` |
  | `mid-error` | отдаёт часть текста, затем событие `error` |
  | `slow` | пауза между чанками 300–800 мс |

  Работает только при `NODE_ENV !== 'production'`.
- **Аборт** обрабатывается честно: пришёл `close` — таймеры гасятся, генерация прекращается.
  Это проверяет тот же путь кода, что потом будет рвать реальный апстрим.

Проверка фазы — `curl -N` по каждому режиму.

## Фаза 2 — UI целиком на моке

Ветка `feat/ui`. Самая большая фаза; внутри — отдельные коммиты по кускам.

**Логика** (`src/lib/`, чистые функции, под тестами):

- `sse.ts` — парсер потока. Один на клиент и сервер.
- `chatReducer.ts` — состояние чатов. Сообщение: `streaming` → `done` | `stopped` | `error`;
  состояние принадлежит чату, не приложению.
- `storage.ts` — `sessionStorage`, запись с дебаунсом, вытеснение старых чатов.
- `streams.ts` — мапа активных потоков по `chatId` вне дерева компонентов: переключение чата
  не должно ронять генерацию.

**Стриминг и отмена** (`src/hooks/useChat.ts`): `fetch` + `body.getReader()` (не `EventSource` —
тот не умеет POST), `AbortController` в ref, оба таймаута на клиенте зеркалят серверные.

**Интерфейс** — раскладка экрана расписана в `docs/ui-structure.md`, токены и перенос
дизайн-системы — в `docs/design-system.md`. Первым делом кладётся `src/styles/tokens.css`,
дальше ни одного хардкода цвета, отступа и радиуса — только `var(--…)`.

- Сайдбар со списком чатов, переключением и фоновой генерацией
- Пустое состояние до первого сообщения — что это, что можно спросить, пара кликабельных примеров.
- Индикатор «модель печатает» на время генерации.
- «Стоп» — кнопка и `Esc`. После остановки интерфейс живой, полученный кусок остаётся в истории.
- Состояния ошибок из контракта, у каждого — текст по-человечески и «Повторить».
- Селектор `:free`-модели. Не требуется заданием, но прямо помогает на 429: сменить модель —
  самое осмысленное действие в этот момент.
- Markdown в ответах модели. Без `rehype-raw`: вывод модели — недоверенный ввод, сырой HTML
  из него в DOM не попадает.
- Адаптив от 320 px.

**Доступность**:

- Семантика: `<main>`, `<ol>`/`<li>`, `<form>`, `<label>`.
- `Enter` отправляет, `Shift+Enter` переносит строку, `Esc` останавливает.
- `aria-live="polite"` — на строке статуса, **не** на тексте ответа. Живой регион, обновляемый
  на каждый токен, превращает скринридер в пулемёт; статус же меняется дискретно:
  «Модель печатает» → «Ответ получен».
- Видимый `:focus-visible` на всём интерактивном (см. «Пушбек»).

**Тесты** — на самое ломкое:

- парсер SSE на кадрах, разрезанных посреди события, и на комментариях-keepalive;
- редьюсер на сценариях «стоп посреди генерации» и «ошибка после частичного текста»:
  в обоих случаях накопленный текст обязан уцелеть.

## Фаза 3 — реальный OpenRouter

Ветка `feat/openrouter`.

Адаптер за тем же контрактом; переключение мок/живой — через env, мок никуда не девается
(на нём остаются воспроизводимыми состояния ошибок).

- `server/env.ts` — валидация на старте, fail-fast: нет ключа в живом режиме — сервер не поднимается
  с внятным сообщением, а не падает на первом запросе.
- Разбор SSE OpenRouter тем же `sse.ts`, отображение в события контракта.
- Дефолтная модель берётся из живого каталога `GET /api/v1/models` с фильтром `:free`
  **на момент реализации** — список меняется, вписывать по памяти нельзя. В коде небольшой
  fallback на случай недоступности каталога.
- Проброс `Retry-After` в `retryAfter` при 429.

Проверка: вкладка Network — запросов на `openrouter.ai` со страницы нет, заголовка `Authorization`
в запросах к своему API нет; `grep` по `dist/` не находит ключ.

## Принятые решения

| Решение | Почему |
|---|---|
| Один `package.json` | Реальному человеку надо запустить проект за пять минут. Workspaces добавляют церемонии без выигрыша на проекте такого размера |
| Чистый CSS + CSS Modules | Задание отдельно просит семантическую разметку, «не div-кашу». Утилитарные классы тянут в обратную сторону. Заодно ноль зависимостей на стилях |
| Нормализованный SSE вместо проброса потока | Ошибку после отправки заголовков иначе не доставить; плюс не течёт наружу форма ответа апстрима |
| История в `sessionStorage` | Переживает промах по F5, но не копит чужие разговоры на общем компьютере. Компромисс между «не терять работу» и «не хранить вечно» |
| Мок-сервер до реальной модели | Обработка краёв — первый критерий оценки, а на живой бесплатной модели она невоспроизводима |
| Отмена доходит до апстрима | Иначе «Стоп» останавливает только показ, а квота продолжает гореть |
| UI по дизайн-системе Nocturne | Готовая тёмная система с продуманными состояниями и токенами — вместо изобретения палитры по ходу. Токены и перенос — в `docs/design-system.md` |
| Одна тема, тёмная | Nocturne — тёмная система; светлый вариант пришлось бы выводить самому, и он не был бы ею |

Решения с контекстом и последствиями разложены по ADR в `docs/adr/`.

## Пушбек

Задание просит не выполнять молча то, что кажется ошибочным, а описать в README.

> Уберите стандартную браузерную обводку фокуса (`outline`) у кнопок и поля ввода.

Требование конфликтует с требованием доступности в том же документе: «интерфейсом можно
полноценно пользоваться с клавиатуры». Без видимого фокуса Tab-навигация вслепую — пользоваться
нельзя.

Выполняем по смыслу, а не буквально: дефолтную обводку снимаем (разнобой между браузерами —
реальная проблема, и хотели явно этого), но каждый интерактивный элемент получает собственное
кольцо через `:focus-visible`. Оно не появляется при клике мышью и появляется при Tab.
Оба требования выполнены, ни одно не нарушено.

## Вне объёма

Сознательно не делаем — не потому что не умеем, а потому что в 2–6 часов это не влезает
и заданием не требуется. В README уходит в «что дальше»: светлая тема и переключатель,
серверное хранение истории, авторизация, локализация, самостоятельный хостинг шрифта,
поиск и переименование чатов, очередь параллельных запросов, регенерация и редактирование
сообщений, выгрузка диалога.

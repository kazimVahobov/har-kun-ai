# 0011 — Несколько чатов и фоновая генерация при переключении

- **Статус:** принято
- **Дата:** 2026-09-29
- **Уточняет:** [0008](0008-session-storage-history.md) — форму хранилища, но не выбор
  `sessionStorage`
- **Дополнено:** [0012](0012-chat-sidebar-scope.md) — несколько чатов идут сверх задания,
  сайдбар делается последним пунктом фазы 2. Решения ниже в силе, меняется только очерёдность

## Контекст

В интерфейс добавился сайдбар со списком чатов и переключением между ними. Отсюда вопрос,
которого при одном диалоге не было: что делать с генерацией, если пользователь ушёл в другой чат,
пока модель отвечает.

Рядом стоял второй вопрос, звучавший как следствие первого: если генерацию продолжать фоново
и при этом писать её в хранилище, не придётся ли писать на каждый символ.

Второй вопрос оказался ложным, и разобраться в нём стоит до решения — иначе можно выбрать
прерывание потока просто из страха перед посимвольной записью.

## Решение

**Генерацию при переключении не прерываем.** Она продолжается фоново, чат помечается точкой
в сайдбаре, по возвращении виден дописанный ответ.

Прерывать хуже по существу: пользователь уже заплатил за ответ ожиданием и квотой бесплатной
модели. Отменять его за то, что человек отвлёкся, — наказание за нормальное поведение.
«Стоп» существует ровно для случая, когда ответ не нужен, и нажимается явно.

**Посимвольная запись не требуется.** Поток живёт в памяти приложения — в сторе вне дерева
компонентов, ключ `chatId`: `AbortController`, читатель и накопленный текст. Переключение чата
меняет только `activeChatId`, то есть что отрисовано; стор и запрос не трогает.

Отрисовка читает из памяти, а не из хранилища. Хранилище нужно ровно для одного — пережить
перезагрузку. А перезагрузка убивает поток в любом случае: `fetch` умирает вместе со страницей.
То есть посимвольная запись сохраняла бы хвост ответа, который после перезагрузки всё равно
оборван и помечен остановленным. Выигрыш — последние сотни миллисекунд текста мёртвого потока,
цена — сериализация всего стора на каждый токен.

Поэтому запись остаётся прежней: дебаунс ~300 мс, немедленный сброс на `done` / `stopped` /
`error` и на `pagehide`. Окно потери — до одного дебаунса текста, уже принадлежащего
оборванному потоку.

**Параллельные потоки разрешены.** Свой `AbortController` на чат. `Esc` и «Стоп» останавливают
только активный чат. Удаление чата сначала абортит поток, потом удаляет.

Форма хранилища меняется с одного диалога на `{ version, activeChatId, chats[] }`,
ключ `har-kun-ai:v1`; потолок — 20 чатов, вытеснение по `updatedAt`.

## Последствия

- Ответ не теряется из-за переключения — сценарий «спросил, пошёл читать другой чат, вернулся»
  работает так, как его ожидают.
- Стор потоков живёт вне React. Это сознательный выход из дерева компонентов: держи поток
  в состоянии компонента — и размонтирование при переключении чата его убьёт. Взамен —
  ручная ответственность за очистку мапы при завершении и удалении чата.
- Несколько одновременных потоков означают несколько одновременных запросов к бесплатной
  модели, а она легко отвечает 429. Жёсткого потолка не ставим: 429 уже полноценно обработан
  и прикреплён к своему сообщению. Очередь запросов — в «что дальше».
- Фоновое завершение ничего не объявляет в `aria-live`: живой регион отражает только активный
  чат, иначе скринридер будет перебивать текущее чтение чужими новостями. Цена — незрячий
  пользователь узнаёт о готовности фонового ответа, только зайдя в него.
- Сайдбар усиливает натяжение в [0008](0008-session-storage-history.md): список чатов выглядит
  как нечто, что должно жить дольше вкладки, а `sessionStorage` его не переживает. Решение
  оставляем — задание говорит про историю «в рамках сессии», и приватность на общем компьютере
  весит больше. Но натяжение реальное, и в README оно проговаривается вместе с обоснованием.

# 0012 — Сайдбар чатов идёт сверх задания и делается последним

- **Статус:** принято
- **Дата:** 2026-09-29
- **Дополняет:** [0011](0011-background-generation.md)

## Контекст

Сайдбар со списком чатов и переключением между ними попал в спецификацию экрана
([`docs/ui-structure.md`](../ui-structure.md)) как требование к интерфейсу. После этого задание
было перечитано на предмет того, откуда это требование берётся.

**Нескольких чатов в задании нет.** Везде единственное число:

| Место | Формулировка |
|---|---|
| Что делаем | «Одностраничный веб-чат с языковой моделью: пользователь пишет сообщение — модель отвечает» |
| Требование 1 | «**Диалог** с моделью через OpenRouter» |
| Требование 3 | «уже полученный кусок ответа остаётся **в истории**» |
| Требование 5 | «**История диалога** в рамках сессии. Переживает ли **она** перезагрузку страницы» |
| Пожелания к UI | «Пустое состояние: что человек видит до **первого сообщения**» |

Ни списка, ни переключения, ни слова «чаты» во множественном числе. Требование 5 — единственное
место про хранение, и там «история диалога… она».

Запрета тоже нет: «Дизайн, структура проекта и стек — на ваш вкус; вкус мы тоже оцениваем».
То есть сайдбар допустим — но целиком сверх требований.

Цена при этом не косметическая. Переключение чатов — это компонент; всё остальное тянется следом:
мапа потоков по `chatId` вне дерева компонентов, выездная панель на мобильном с ловушкой фокуса,
разбор приоритета `Esc`, индикаторы фоновой генерации и непрочитанного, удаление с отменой,
вытеснение чатов по квоте хранилища. Порядка полутора-двух часов из бюджета в 2–6.

Тратятся они на то, что не попадает ни в один из первых четырёх критериев оценки:
работоспособность и края → инженерные решения → процесс → суждение → вкус. Сайдбар ложится
только в пятый. И отчасти работает против первого: параллельные потоки на бесплатной модели —
это больше 429 и больше способов сломаться ровно там, где оценивают строже всего.

## Решение

Сайдбар остаётся в объёме, но **делается последним пунктом фазы 2** — после того как стриминг,
отмена, обработка краёв и доступность работают и проверены.

При этом **форма данных многочатовая с самого начала**: стор `{ version, activeChatId, chats[] }`
и мапа потоков по `chatId`. Это почти ничего не стоит на старте и снимает главный риск —
переделку архитектуры в конце, под цейтнот.

Порядок внутри фазы 2: логика и тесты → композер и стриминг → состояния ошибок → доступность
и адаптив → отделка → **сайдбар**.

Не успели — в README словами, как задание прямо разрешает: «Что не успели — опишите в README
словами, это нормальный исход».

## Последствия

- Бюджет тратится в порядке, совпадающем с порядком оценки. Если время кончится, кончится оно
  на необязательном, а не на требуемом.
- Архитектура не требует переделки, когда очередь до сайдбара дойдёт: данные уже той формы.
  Цена — многочатовая структура живёт какое-то время при одном чате, то есть чуть сложнее,
  чем нужно прямо сейчас.
- Есть и обратная сторона, которую честно стоит назвать: критерий «суждение» оценивает в том
  числе трактовку задания, и осознанно добавленный сайдбар с объяснением в README — скорее плюс,
  чем минус. Мы не отказываемся от него, только переставляем в очереди.
- Расхождение с заданием уходит в README отдельным абзацем — рядом с пушбеком про `outline`
  ([0007](0007-custom-focus-ring.md)). Разница между ними существенная и её стоит проговорить:
  там мы отступили от буквы, чтобы выполнить требование по смыслу; здесь — добавили то,
  чего не просили. Молча оставлять не следует ни то, ни другое.
